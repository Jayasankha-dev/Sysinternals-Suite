Network Forensics & Practical Incident Response

Network evidence can expose behavior that endpoint tools fail to explain. The goal is to understand which process communicated, where it connected, when it connected, and whether the communication fits the system's role.

6.1 TCPView

TCPView provides a live view of TCP and UDP endpoints. Use it to map active connections to processes and identify unexpected destinations or listening services.

6.2 Practical Suspicious-File Workflow

  1. Do not execute an unknown file on a production endpoint simply to “see what happens.”
  2. Record file name, path, hash, source, timestamps, and user context.
  3. Determine whether the file is expected for the installed application.
  4. If dynamic analysis is authorized, use an isolated laboratory or sandbox.
  5. Observe process creation, file changes, registry changes, and network activity.
  6. Correlate telemetry into a timeline.
  7. Contain according to incident-response procedures.
  8. Preserve relevant evidence before cleanup where feasible.

6.3 Network Indicators

Useful indicators include unusual destinations, periodic beacon-like timing, unexpected protocols, newly observed domains, abnormal DNS behavior, and a process communicating in a way inconsistent with its function.

6.4 Incident Response

Contain

Reduce the ability of the suspected system to cause further harm while preserving evidence and business continuity.

Eradicate & Recover

Remove the cause, restore trusted state, validate controls, and monitor for recurrence.

6.5 Reporting

A useful incident report separates observed facts from analyst interpretation. Include timestamps, evidence identifiers, affected assets, confidence, actions taken, and unresolved questions.
