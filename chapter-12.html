Reverse Engineering for Defenders

Reverse engineering turns a compiled artifact into evidence. The objective of defensive RE is to understand what a program is designed to do, how it behaves, and whether that behavior is consistent with its stated purpose.

12.1 Static Analysis

Begin with file type, architecture, hashes, metadata, strings, imports, exports, embedded resources, and signatures. Tools such as Detect It Easy, PE-bear, Ghidra, and similar analyzers can help identify structure.

12.2 Dynamic Analysis

Execute only in an isolated, authorized laboratory. Observe process trees, file changes, registry activity, network communication, mutexes or synchronization objects, and persistence behavior.

12.3 Ghidra Workflow

  1. Import the sample into an isolated project.
  2. Identify architecture and entry points.
  3. Review strings and imported APIs.
  4. Use the decompiler to understand relevant functions.
  5. Rename functions and variables as understanding improves.
  6. Correlate static findings with observed runtime behavior.

12.4 PE Structure

Windows Portable Executable files contain headers, sections, imports, exports, resources, and other metadata. Abnormal section names, permissions, overlays, or unusual import patterns can be useful investigation leads.

12.5 Anti-Analysis

Malware may detect debuggers, sandboxes, or analysis artifacts. From a defender's perspective, treat anti-analysis behavior as a finding and use multiple independent observations rather than attempting to defeat protections on a real target.
