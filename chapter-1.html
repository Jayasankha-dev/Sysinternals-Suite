Foundations of Windows
Threat Hunting

Threat hunting begins with a simple idea: suspicious activity becomes easier to recognize when you understand what normal activity looks like.

Learning objectives
By the end of this chapter you should be able to describe common Windows threat vectors, explain the role of scripts and C2 communications, distinguish live monitoring from post-incident forensics, and build a useful baseline for a Windows endpoint.

1.1 Understanding Threat Vectors & Script-Based Attacks

A threat vector is the route or technique through which an attacker, malicious program, or unwanted action reaches a system. On Windows endpoints, this can involve phishing attachments, malicious documents, compromised installers, browser downloads, removable media, exposed services, stolen credentials, or scripts launched through trusted interpreters.

Script-based attacks deserve special attention because the attacker may not need to introduce a traditional executable immediately. A script can act as a loader, download additional content, modify configuration, create persistence, or invoke legitimate Windows components. Common interpreters include PowerShell, Windows Script Host components, and command shells.

How a script-based intrusion can unfold

  1. Initial delivery: a user receives a file, link, archive, or other content.
  2. Execution: the user or another process launches the content.
  3. Staging: the script may create temporary files, configuration data, or additional payloads.
  4. Discovery: the activity may query processes, accounts, network configuration, or other system information.
  5. Communication: the process may attempt to reach an external service for instructions or data transfer.
  6. Persistence or follow-on activity: the actor may attempt to survive reboot or continue operating through another process.

For a defender, the important question is not simply “Was a script executed?” Instead, ask: Who launched it, from where, with which parent process, what did it touch, and what happened immediately afterward?

Analyst mindset: a single event rarely proves compromise. Strong findings usually come from connecting process, file, registry, user, and network evidence into a timeline.

Recognizing suspicious script activity

Useful indicators include an unusual parent-child relationship, execution from a temporary or user-writable directory, an unexpected script launched by an office application, newly created files followed by outbound connections, or a process whose name resembles a legitimate Windows component but whose path is unexpected.

These indicators should be treated as leads rather than automatic proof of maliciousness. Administrators, software updaters, management agents, and security tools can also generate unusual-looking activity.

1.1.1 Command & Control (C2)

Command and Control describes the communication channel through which an operator or malicious infrastructure can influence a compromised system. C2 traffic can be direct or hidden within ordinary-looking protocols and services.

Threat hunters therefore look beyond the existence of a network connection. Useful context includes the initiating process, destination, timing, frequency, DNS activity, remote port, executable path, user context, and whether the connection is consistent with the endpoint's normal role.

Example investigation questions
Which process opened the connection?
What is the process's executable path?
Who owns the process?
Was the process recently created?
Is the destination expected for this application?
Did file or registry activity occur before the connection?

1.2 The Mindset of a Security Analyst

Threat hunting is an evidence-driven discipline. Analysts continuously form hypotheses, test them against telemetry, and revise their conclusions as new evidence appears. The objective is not to label every unusual event as malicious; it is to reduce uncertainty using reliable evidence.

Live monitoring vs. post-incident forensics

Live monitoring

Focuses on what is happening now. It is useful for observing process creation, resource usage, connections, and system changes while an event is active.

Post-incident forensics

Focuses on reconstructing what happened. Analysts examine logs, timestamps, artifacts, persistence locations, hashes, and other preserved evidence.

The two approaches complement one another. Live monitoring can capture transient behavior that disappears quickly, while forensic analysis can provide a broader historical timeline.

Establishing a healthy Windows baseline

A baseline is a documented picture of expected behavior. It can include normal processes, installed software, startup entries, scheduled tasks, listening services, typical network destinations, and expected resource usage.

Baselines should be role-specific. A developer workstation, domain controller, file server, and kiosk can have very different normal behavior. A good baseline therefore records context instead of relying on a universal “safe process list.”

Chapter summary

Windows threat hunting is fundamentally about context and correlation.
